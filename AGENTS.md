# Working on hook-atlas

## Stop and ask

**If something is hard to walk back, pause and ask before doing it.** Not after.

This is the most important rule here, and it is written down because the
alternative is common: an agent on auto-pilot, a user hitting enter, and a
decision nobody actually made. You are not being helpful by guessing on these.

Ask before:

- **publishing anything** - a PyPI release, a tag, a GitHub release. A version
  number on PyPI cannot be reused, ever, even after deletion.
- **pushing to `main`**, in this repo or any other. Work on a branch and hand
  over the link.
- **rewriting history** - force pushes, rebases of shared branches, amending a
  commit somebody may already have.
- **deleting or overwriting anything generated by a real run** - traces,
  captures, committed fixtures. Re-running is not the same as restoring.
- **changing a public interface** other code already depends on. There is a
  consumer, and it is `pytest-hook-atlas`.
- **changing what gets recorded** - the trace schema, what a fingerprint covers,
  what counts as a phase. These invalidate existing data, and the cost lands on
  whoever has to re-capture.
- **adding a dependency**, especially to the runtime package. This library gets
  installed into other people's environments.

Also stop and say so, rather than pressing on, when:

- the task as asked would not do what the user seems to want,
- you have found a second, better way to do it and the user has not seen it,
- you are about to do something expensive - a long capture, a big re-run - and a
  cheaper check would settle the question first,
- you are guessing. Say you are guessing, and say what would settle it.

Being told "go ahead" once is not blanket permission for everything after it.
Ask again when the next irreversible thing comes up.

## Verify against reality, not your own output

A green test run says the tests passed, not that the thing works. This project
has shipped a stylesheet whose selectors matched nothing and a preview image
that proved nothing, both with CI green.

Where a claim can be measured, measure it and quote the number. Where it cannot,
say that it cannot.

The clearest example lives in CI: the applications jobs run tox, datasette,
devpi-client and pytest for real. The first run against datasette's own test
suite found a crash - its tests chdir into temporary directories and delete
them, so `os.getcwd()` raised inside the tracer. No synthetic fixture we wrote
would have done that, which is exactly why those jobs use real projects.

## Do not write down numbers that expire

Line numbers, file sizes, ratios, "N of M". They are true when written and wrong
a few commits later, and a stale number is worse than none because it gets
believed. Say what to do and why; let whoever picks it up measure it.

Commit messages and changelog entries are the exception - they describe a moment
that has already passed, so a number in them stays true.

## What belongs in this package

Nothing that knows what application it is looking at. No `import pytest`, no
pytest hook names in logic, no assumptions about phases, documentation URLs or
which plugins are "internal". CI fails if the package imports pytest at all.

pytest's four phases, its documentation links and its scenarios live in
[pytest-hook-atlas](https://github.com/zy1o/pytest-hook-atlas), which is the
first consumer and the reason most of this code exists. Naming pytest in a
comment as an *example* is fine and often the clearest thing to do. Depending on
it is not.

An application nobody has described must still produce something useful: one
diagram of the whole run, hooks unlinked, no phases invented. That guarantee is
tested in `tests/test_unconfigured.py`; do not let it rot.

## Leave the traced program alone

The tracer runs inside somebody else's process. It must never change what that
program does:

- its exit code is its own - a wrapper that turns a failing run into a passing
  one is worse than no wrapper, and there is a test named for it,
- its stdout is its own; diagnostics go to stderr,
- an error inside the tracer must not escape into the program. Capture is
  forgiving on purpose; strictness belongs in `hook_atlas.validate`, which runs
  afterwards where failing is free.

## House style

- **Explain *why* in comments**, not what. Most non-obvious code here exists
  because something failed in a particular way. Say which.
- Tests are named for the behaviour they protect, not the function they call.
- Keep changelog entries to a line or two; the commit message is where the long
  version goes.

## Commands

```bash
pip install -e ".[dev]"          # plus -e ../hook-atlas in the consumer repo
pytest -q                        # unit tests; application tests are opt-in
pytest -q -m applications        # runs real programs, needs them installed
python -m hook_atlas.validate t.json
ruff check src/ tests/ && ruff format --check src/ tests/
```
